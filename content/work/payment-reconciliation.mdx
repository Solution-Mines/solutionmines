approach: >-
  We modelled the ledger first and treated each payment source as an untrusted
  feed into it, rather than trying to make three systems agree directly with
  each other. Matching runs in passes — exact reference, then amount and date
  window, then fuzzy — with anything unmatched surfaced for review rather than
  guessed at.
outcome: >-
  The weekly reconciliation became a scheduled job with an exceptions queue.
  Unmatched items are surfaced the next morning instead of at month end, which
  is the change that actually mattered: errors are now found while the context
  is still fresh.
decisions:
  - title: One canonical ledger, not three-way matching
    chose: A single internal ledger that each source feeds into, with source-specific adapters.
    tradeoff: More upfront modelling, and an extra hop for every payment. In exchange, adding a fourth payment source later is an adapter rather than a rewrite of the matching logic.
  - title: Matching in passes, with a confidence threshold
    chose: Exact match first, then progressively looser passes, with anything below the threshold queued for a person.
    tradeoff: Some items still need human review. Automating those too would have meant accepting silent mis-matches, which in a financial context is worse than the manual work.
  - title: Deliberately not real-time
    chose: A scheduled overnight run rather than event-driven reconciliation.
    tradeoff: Figures are a day behind. That was acceptable here and removed an entire class of ordering and partial-failure problems that real-time would have introduced.

## What we found

Discovery turned up something the brief had not mentioned: the marketplace
payout was already net of fees, while the card processor reported gross with a
separate fee line. The spreadsheet had been silently absorbing that difference
for over a year, which meant the historical figures everyone trusted were
slightly wrong in a consistent direction.

That changed the job. Before building anything we agreed a position on
historical data: the backfill would restate it rather than preserve the
existing numbers, and the difference would be reported rather than quietly
corrected.

## What we built

A ledger service with one adapter per payment source, a matching engine that
runs in passes, and an exceptions queue with enough context attached that a
non-technical user can resolve an item without opening another system.

The backfill was written to be resumable from the start, which proved
necessary — the first run was interrupted twice.
