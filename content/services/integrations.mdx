## How we approach it

An integration is a promise that two systems will agree. Most integrations
break because that promise was never written down — only implied by whatever
the first version of the code happened to do.

### The hard parts we take a position on

**Partial failure is the normal case, not the edge case.** Any integration that
assumes the other side is up, fast and correct will fail in production. We
design for retries, for out-of-order delivery, and for the same message
arriving twice — which is why idempotency keys are not optional.

**Someone has to own each field.** When two systems can both write a customer's
address, you do not have an integration, you have a race. Deciding which system
is authoritative for what is the real work; the code is downstream of it.

**Silence is the worst failure mode.** An integration that throws loudly gets
fixed the same day. One that quietly stops at 02:00 gets discovered when
someone notices the numbers are wrong, and by then the backfill is the expensive
part. Monitoring is part of the build, not a later phase.
