## How we approach it

Inheriting a system is mostly an archaeology problem. The code tells you what
it does; it rarely tells you why, and almost never tells you which parts
somebody depends on in a way nobody wrote down.

So we do not start by changing things. We start by making the system
observable and reproducible: getting it building on a clean machine, getting a
deployment that is not a sequence of remembered steps, and pinning current
behaviour with tests.

### The hard parts we take a position on

**Get it building before you get it good.** A system you cannot deploy
confidently cannot be improved safely, because you have no way to tell whether
your change or the deployment broke it.

**Characterise before you refactor.** Tests written against current behaviour —
including the behaviour that looks like a bug — are what let you change code
you do not fully understand. Some of those bugs are load-bearing.

**Rewrites are a last resort, and we will argue against yours.** The second
system is rarely simpler, and during the rewrite you are paying for two systems
while shipping no new value. Strangling the risky parts incrementally is slower
to describe and far faster to deliver.
